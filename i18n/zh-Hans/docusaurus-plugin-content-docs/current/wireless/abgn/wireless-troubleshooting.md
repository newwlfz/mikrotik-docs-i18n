# 无线故障排查

> 本页介绍如何通过启用和分析 MikroTik RouterOS 中详细的调试日志，来排查无线连接问题，包括客户端连接、断开以及 MIC 失败或雷达检测等安全事件。

# 无线故障排查

## 无线调试日志

使用日志调试无线问题。

默认情况下，RouterOS 无线日志仅显示客户端连接和断开的简单条目：

```ros
22:32:18 wireless,info 00:80:48:41:AF:2A@wlan1: connected
```

对于普通用户来说，知道 MAC 地址为 "00:80:48:41:AF:2A" 的无线客户端已连接到无线接口 "wlan1" 就足够了。但实际上，标准日志中显示的条目之外还有更多可用的日志条目。它们被称为“调试”日志，提供更详细的信息。在下面的调试日志示例中，您将看到同一客户端连接到 AP 的详细过程，比典型日志更详细：

```ros
22:33:20 wireless,debug wlan1: 00:80:48:41:AF:2A attempts to connect
22:33:20 wireless,debug wlan1: 00:80:48:41:AF:2A not in local ACL, by default accept
22:33:20 wireless,info 00:80:48:41:AF:2A@wlan1: connected
```

调试日志将为您提供客户端无线连接和断开过程中每个步骤的更具体信息。第一行显示无线客户端尝试连接到 AP。第二行显示 AP 检查该客户端是否被允许连接到 AP，并显示结果操作。只有在第三行您才看到客户端已连接。这仅仅是调试日志消息的一个示例。所有调试条目的描述如下。

要启用无线调试日志，您应执行以下命令：

```ros
[admin@MikroTik] > /system/logging                                            
[admin@MikroTik] /system/logging> add topics=wireless,debug action=memory
```

这将帮助您轻松理解和修复无线问题，减少与支持团队的交互。

### 工作站模式

```ros
<MAC>@<DEV>: lost connection, <REASON>
```

工作站因 \<REASON\> 而失去与 AP 的连接。

```ros
<MAC>@<DEV>: failed to connect, <REASON>
```

工作站尝试连接到 AP，但因 \<REASON\> 而失败。

```ros
<MAC>@<DEV>: established connection on <FREQ>, SSID <SSID>
```

工作站尝试并成功连接到 SSID 为 \<SSID\>、频率为 \<FREQ\> 的 AP。

```ros
<MAC>@<DEV>: MIC failure!!!
```

TKIP 消息完整性检查失败，可能有人试图入侵或对网络进行拒绝服务攻击。如果在 60 秒内遇到超过 1 次 MIC 失败，将进入“TKIP 对策”状态。

```ros
<MAC>@<DEV>: enter TKIP countermeasures
```

进入 TKIP 对策状态，这意味着工作站将从 AP 断开并静默 60 秒。

### AP 模式

```ros
<DEV>: radar detected on <FREQ>
```

在频率 \<FREQ\> 上检测到雷达，AP 将寻找其他信道。

```ros
<DEV>: data from unknown device <MAC>, sent deauth [(XXX events suppressed, YYY deauths suppressed)]
```

收到来自未知设备（即未注册到此 AP 的设备）MAC 地址为 \<MAC\> 的数据帧，AP 向其发送了去认证帧（根据 802.11 标准）。XXX 是未记录的日志事件数量，以防止日志过大（前 5 条后，日志限制为每 5 秒 1 条）；YYY 是应发送但未发送的去认证帧数量，以避免浪费资源发送过多去认证帧（每秒仅允许 10 个去认证帧）。

此类消息的可能原因是：工作站之前连接到 AP，但 AP 尚未意识到该工作站已从注册表中删除，工作站仍在向 AP 发送数据。去认证消息告知工作站其已不再连接。

```ros
<DEV>: denying assoc to <MAC>, failed to setup compression
```

AP 上初始化压缩失败，最可能是因为尝试连接并使用压缩的客户端过多。

```ros
<DEV>: <MAC> is new WDS master
```

WDS 从设备已建立到 WDS 主设备的连接，这意味着 WDS 从设备开始接受客户端并充当 AP。

```ros
<DEV>: <MAC> was WDS master
```

此消息在与 \<MAC\> 的连接断开后出现，意味着 WDS 从设备将断开所有客户端并开始扫描以寻找新的 WDS 主设备。

```ros
<MAC>@<DEV>: connected [, is AP][, wants WDS]
```

地址为 \<MAC\> 的工作站已连接。如果存在 "is AP"，则表示远程设备是 AP；如果存在 "wants WDS"，则表示远程设备希望建立 WDS 链路。

```ros
<MAC>@<DEV>: disconnected, <REASON>
```

与地址为 \<MAC\> 的工作站的连接因 \<REASON\> 而终止。

```ros
<DEV>: TKIP countermeasures over, resuming
```

TKIP 对策（60 秒静默期）结束，AP 恢复作为 AP 运行。

```ros
<DEV>: starting TKIP countermeasures
```

进入 TKIP 对策状态（60 秒静默期），所有客户端将断开连接。

### \<REASON\>

**"joining failed"** - 仅可能发生在 Prism 网卡的工作站模式下，因某种原因未能连接到 AP。

**"join timeout"** - 发生在工作站上，未能与 AP 同步（接收第一个信标帧）。最可能是信号太弱、远程设备关闭、强干扰或其他射频相关问题导致通信无法进行。

**"no beacons"** - 未从 WDS 链路远端收到信标。最可能是信号太弱、远程设备关闭、强干扰或其他射频相关问题导致通信无法进行。

**"extensive data loss"** - 本地接口因在最低速率下多次发送失败后无法向远程设备发送数据，决定断开与远程设备的连接。可能原因：信号太弱、远程设备关闭、强干扰或其他射频相关问题导致通信无法进行。

**"decided to deauth, \<802.11 reason\>"** - 本地接口决定使用 802.11 原因码 \<802.11 reason\> 对远程设备进行去认证。

**"inactivity"** - 远程设备长时间不活动。

**"device disabled"** - 本地接口被禁用。

**"got deauth, \<802.11 reason\>"** - 收到来自远程设备的去认证帧，802.11 原因码在 \<802.11 reason\> 中报告。

**"got disassoc, \<802.11 reason\>"** - 收到来自远程设备的去关联帧，802.11 原因码在 \<802.11 reason\> 中报告。

**"auth frame from AP"** - 收到来自已知为 AP 的远程设备的认证帧，最可能是远程设备模式从 AP 更改为工作站。

**"bad ssid"** - WDS 链路的 SSID 错误。

**"beacon from non AP"** - 收到来自已知为非 AP 节点的远程设备的信标帧，最可能是远程设备模式从工作站更改为 AP。

**"no WDS support"** - 未报告 WDS 支持。

**"failed to confirm SSID"** - 未能确认 WDS 链路另一端的 SSID。

**"hardware failure"** - 某些硬件故障或意外行为。不太可能看到。

**"lost connection"** - 仅可能发生在 Prism 网卡的工作站模式下，因某种原因失去与 AP 的连接。

**"auth failed \<802.11 status\>"** - 发生在工作站上，AP 拒绝认证，802.11 状态码在 \<802.11 status\> 中报告。

**"assoc failed \<802.11 status\>"** - 发生在工作站上，AP 拒绝关联，802.11 状态码在 \<802.11 status\> 中报告。

**"auth timeout"** - 发生在工作站上，工作站未收到认证帧的响应，可能是链路质量差或 AP 因某种原因忽略此工作站。

**"assoc timeout"** - 发生在工作站上，工作站未收到关联帧的响应，可能是链路质量差或 AP 因某种原因忽略此工作站。

**"reassociating"** - 发生在 AP 上，由于已被视为关联的工作站尝试再次关联，因此假定连接已丢失。必须删除所有与连接相关的信息，因为在关联过程中会协商连接参数（因此显示“已断开”）。工作站重新关联的原因应在工作站上查找（最可能的原因是工作站因某种原因断开连接而未告知 AP——例如数据丢失、配置更改）。

**"compression setup failure"** - 连接无法建立，因为没有足够的资源进行压缩（已连接太多想要使用压缩的工作站）。

**"control frame timeout"** - AP 无法向客户端传输（类似于 802.11 协议中看到的错误消息——大量数据丢失）。

### \<802.11 reason\> 和 \<802.11 status\>

这些是编码在 802.11 管理消息中的数字原因/状态码。日志消息包含数字代码和来自 802.11 标准组中相应标准的文本描述。尽管这些描述尽可能详细，但必须考虑到管理帧中出现的实际原因/状态码完全取决于设备或软件制造商——一个设备可能发送包含适当原因/状态码的 802.11 管理帧，而另一个设备可能发送带有“未指定”原因/状态码的帧。因此，原因/状态码应仅视为参考信息。

随着 802.11 标准的发展，RouterOS 可能缺少某些设备使用的原因/状态码的文本描述。在这种情况下，应使用数值在 802.11 标准中查找含义。

为了正确解释原因/状态码，需要充分理解 802.11 组标准。大多数文本描述是不言自明的。以下是一些最常见原因/状态码的解释：

- **class 2 frame received (6)** - 设备在完成 802.11 认证过程之前收到了“class 2”帧（关联/重新关联管理帧）；

- **class 3 frame received (7)** - 设备在完成关联过程之前收到了“class 3”帧（数据帧）。

## 无线常见问题解答

### 设置

**为什么我的 Apple Mac 设备无法连接到 MikroTik 802.11n AP？**

此问题仅出现在基于 Broadcom 无线芯片组的 Mac 设备上。要使用此类无线设备连接到 MikroTik 802.11n AP，请确保不要使用 'short' 前导码模式。使用 'long' 或 'both' 前导码模式，Mac 无线设备将能够连接。

**更改某些无线设置后，无线链路工作不稳定。**

有时，当您更改某些无线设置以调整链路时，可能会使链路无法建立或工作不稳定，而您不记得最初的设置。在这种情况下，您可以在无线菜单中使用 *reset-configuration* 命令——它将重置特定无线接口的所有无线设置，您可以从头开始配置接口。请注意，执行此命令也会禁用接口，因此如果您正在通过要重置配置的无线链路远程配置路由器，请务必小心不要执行此命令。

**什么是无线重传，在哪里检查？**

无线重传发生在接口发送帧但未收到确认（ACK）时，导致其尝试再次发送帧，直到收到确认或达到数据包的最大允许重传次数。无线重传会增加无线链路的延迟并降低吞吐量。发生的重传次数可以通过从注册表中给定条目的 **hw-frames** 参数值中减去 **frames** 参数值来确定。一定数量的重传是预期的，但如果 **hw-frames** 的值多次超过 **frames** 的值，则无线链路存在问题，需要排查。

**我也可以在 Nstreme 链路上比较 frames 和 hw-frames 吗？**

**frames** 仅计算包含实际数据的帧。在 Nstreme 的情况下，如果没有其他数据要发送，则单个帧中只能传输 ACK。这些 ACK 帧不会计入 **frames** 计数，但会出现在 **hw-frames** 中。如果双向流量都以最大速度传输（例如，不会有仅 ACK 的帧），则不能像常规无线链路那样比较 **frames** 和 **hw-frames**。

**我可以使用哪些 TX-power 值？**

tx-power 默认设置是网卡可以使用的最大发射功率，取自网卡的 eeprom。如果您想使用更大的 tx-power 值，您可以设置它们，但**风险自负**，因为它最终可能会损坏您的网卡！通常，应仅使用此参数来降低 tx-power。

一般来说，tx-power 控制属性应保留默认设置。更改默认设置在某些情况下可能对某些网卡有帮助，但未经测试，最常见的结果是范围和吞吐量下降。可能发生的一些问题包括：

- 功率放大器芯片和网卡过热将导致效率降低和更多数据错误；
- 过度驱动放大器将导致更多数据错误；
- 网卡功耗过大可能会使网卡所在板的 3.3V 电源过载，导致电压下降、重启或板卡温度过高。

**哪种 TX-power-mode 最好？**

*TX-power-mode* 告诉无线网卡应使用哪些 tx-power 值。默认情况下，此设置设为 *default*。

- **default** 表示网卡将使用网卡 eeprom 中的 tx-power 值，并忽略用户在 *tx-power* 字段中指定的设置。
- **card-rates** 表示对于不同的数据速率，tx-power 根据网卡 eeprom 中的网卡发射功率算法计算，并以用户指定的 *tx-power* 值作为参数。
- **all-rates-fixed** 表示网卡将对所有数据速率使用用户在 *tx-power* 字段中指定的一个 tx-power 值。

请注意，不建议使用 'all-rates-fixed' 模式，因为无线网卡对较高数据速率的 tx-power 较低，强制对较高数据速率使用固定 tx-power 速率可能会导致与上一个关于 tx-power 设置的问题中相同的问题。对于 MikroTik Radio 设备，功率不会高于 EEPROM 中写入的功率。在大多数情况下，如果您想更改 tx-power 设置，建议使用 *tx-power-mode=card-rates*，并建议降低而不是提高 tx-power。对于 AR9300 及更新的 Atheros 无线芯片组，"tx-power-mode=all-rates-fixed" 是唯一选项，因为 "card-rates" 选项在这些芯片组上不起作用。

**什么是 CCQ，值是如何确定的？**

客户端连接质量（CCQ）是一个百分比值，显示带宽相对于理论最大可用带宽的使用效率。CCQ 是 Tmin/Treal 值的加权平均值，为每个传输的帧计算，其中 Tmin 是以最高速率无重试传输给定帧所需的时间，Treal 是实际传输帧所需的时间（考虑到传输帧所需的重试次数和传输速率）。

**什么是 hw-retries 设置？**

发送帧时重试的次数，不将其视为传输失败。失败时降低数据速率并再次发送帧。在最低支持速率下连续三次失败将暂停向此目的地的传输，持续时间为 *on-fail-retry-time*。之后，再次发送帧。帧将被重传，直到传输成功，或直到客户端在 *disconnect-timeout* 后断开连接。如果在此期间超过 *frame-lifetime*，帧可能被丢弃。在 Nstreme 的情况下，不使用 "on-fail-retry-time"、"disconnect-timeout" 和 "frame-lifetime" 设置。因此，在最低支持速率下连续三次失败后，无线链路将以“大量数据丢失”消息断开。

**什么是 disconnect-timeout 设置？**

此间隔从最低数据速率下的第三次发送失败开始测量。此时，最低数据速率下的 3 \* (*hw-retries* + 1) 次帧传输已失败。在 *disconnect-timeout* 期间，将以 *on-fail-retry-time* 间隔重试数据包传输。如果在 *disconnect-timeout* 期间无法成功传输任何帧，则连接关闭，此事件记录为“大量数据丢失”。成功的帧传输会重置此计时器。

**什么是 adaptive-noise-immunity 设置？**

自适应噪声免疫（ANI）动态调整各种接收器参数，以最小化干扰和噪声对信号质量的影响。此设置已添加到 Atheros AR5212 及更新芯片组网卡的无线驱动中。

**当使用访问列表或连接列表时，无线设备如何测量信号强度？**

报告的信号电平是平滑因子为 50% 的指数加权移动平均值。

**RouterOS 无线支持哪些纠错方法？**

ARQ 方法在 nstreme 协议中受支持。常规 802.11 标准不包括 ARQ——损坏帧的重传基于确认协议。RouterOS 支持前向纠错编码（卷积编码），编码速率：1/2、2/3 或 3/4。

**配置 RouterOS 设备用于 160MHz 使用。**

如果 RouterOS 设备支持 4x4 传输，除了设置 160MHz 信道宽度外，请确保在无线接口上设置 "rate-set=default"，以便所有流都可用。

如果客户端不支持扩展 NSS，只能进行 2x2 传输，请设置 "vht-supported-mcs=mcs0-9,mcs0-9,none"。

### 设置方案

**放大器会提高我的链路速度吗？**

这取决于您的信号质量和噪声。请记住，使用低输出功率设置和良好的天线，您可能获得更好的链路。放大器会增加噪声，只会给链路带来问题。

放大器会同时增强传输**和**接收信号。因此，在“安静”区域，即您独自一人或“噪声”或“竞争”很少的地方，您可能会获得出色的结果。另一方面，在无线活动频繁的拥挤区域，您也会增加从每个其他竞争者或噪声源接收到的信号，这可能会显著降低链路的整体质量。此外，请考虑 EIRP 以确保您的链路保持在法律限制内。

您也可以在“仅 11b”无线电上获得更好的信号，这些无线电将大多数 802.11g 视为“噪声”，从而更好地过滤可用信号。

**如何使用 hw-retries 微调无线链路？**

您应该理解，对于 802.11 设备，可用于调整其行为的“反馈”信息非常有限：

- 信号强度，可用于根据接收器灵敏度确定最佳传输速率。但这并不可靠，因为不同接收器的灵敏度不同（例如，随时间变化），路径条件不对称（设备只能测量其接收到的信号强度）等。
- 通过接收/不接收发送帧的确认。

考虑到使用信号强度不可靠，802.11 设备基本上只剩下一个“反馈”来调整其操作——传输的成功/失败。当传输失败（未及时收到 ACK）时，发送方无法确定失败原因——无论是噪声、多径、直接干扰（以及这是否干扰了实际数据帧或 ACK 本身）——帧只是没有送达，通常“为什么”并不重要。重要的是数据包错误率。

因此，RouterOS 实现了一种算法，通过仅使用这些有限信息，尝试在任何环境中最有效地利用介质，同时允许用户控制算法的工作方式并描述算法。并且只有一些使用指南，而不是一组在特定情况下应使用的值。

一般来说——*hw-retries* 越大，设备获得的关于介质在特定速率下传递帧能力的“反馈”越好（例如，如果以 54mbps 速率发送帧失败 16 次，比失败 2 次重试提供更多信息），并且越能确定最佳传输速率，但代价是可能引入网络延迟——因为在所有失败重试期间，此信道中的其他设备无法发送。因此，对于 ptp 骨干链路，可以建议使用**更大**的 *hw-retries*——因为已知链路必须始终在线。**更少**的 *hw-retries* 使速率选择适应更快，但牺牲一些准确性（在大多数情况下低于 2 不合理），这可以建议用于 ptmp 链路，其中链路连接/断开是正常的，保持低延迟很重要。

*on-fail-retry-time* 和 *disconnect-timeout* 控制设备在多大程度上将远程方视为“已连接”。更大的 *disconnect-timeout* 将使设备即使以最小可能传输速率存在大量丢失，也不会“断开”对方。这对于已知“必须”建立的“弱”链路（例如骨干链路）最有用。在 ptmp 网络中，大的 *disconnect-timeout* 将再次增加网络延迟，例如 AP 将尝试向刚刚被禁用的某个客户端发送数据（AP 将在整个 *disconnect-timeout* 期间尝试这样做）。

*frame-lifetime* 允许调整 AP 在认为不值得传递帧之前尝试使用帧进行传输的时间（例如，如果以最低可能速率发送帧失败，则启用 *on-fail-retry-time* 计时器。如果在此期间 *frame-lifetime* 到期，则丢弃特定帧，下一次传输尝试将使用下一帧。禁用 *frame-lifetime* 意味着无线将确保“所有”数据帧的有序传递，无论需要多长时间，“或”如果一切失败则断开连接）。这允许针对不同类型的流量进行优化，例如，对于实时流量——如果无线网络的主要用途是例如 voip，则限制 *frame-lifetime* 是合理的，因为 voip 对少量丢失的容忍度高于高延迟。

**是否可以使用仅一个无线电接口的无线中继器？**

此设置可以通过在 ap-bridge 模式下运行的无线接口上使用 WDS 来实现。在较新的 RouterOS 版本中，可以配置无线中继器模式。

**Nv2 无线链路频繁断开。**

当 Nv2 无线链路经历断开，并且日志部分中大多数消息为 'control frame timeout' 时，如果链路信号强，您可以尝试降低无线网卡的发射输出功率。我们建议使用 tx-power-mode=card-rates 来降低无线网卡的 tx-power。如果问题继续，请尝试使用干扰较少的其他无线频率。如果这也没有帮助，请联系 [support@mikrotik.com](mailto:support@mikrotik.com)，并提供断开后从受影响的 AP 和工作站生成的 support output 文件。
